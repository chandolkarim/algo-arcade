# 정찬민의 홈페이지 · 알고리즘 오락실

기술개발연구프로젝트(2026-2) 개인 홈페이지 과제입니다.

## 1. 목적

**알고리즘 연구와 전략 의뢰소.** 첫 화면에는 수업 프로젝트의 질문·기여·AI 활용·검증 사례를 소개합니다. 구현해 보고 싶은 매매 전략을 메일로 받아, 규칙을 숫자로 함께 정리하고, 코드로 만들어 실제 과거 데이터로 백테스트한 뒤 결과 페이지로 공개합니다. 잘 안 된 결과도 그대로 공개합니다. 지금까지 만든 전략·검증 7개가 “이렇게 결과를 받게 된다”는 예시(결과물)이고, 예측 게임 2개는 따로 “게임” 페이지에 있습니다.

- 무료, 연구·교육 목적. 과거 데이터 백테스트·모의 기록만 다룹니다.
- 하지 않는 것: 돈을 받는 일, 특정 종목 추천·매매 신호 발송, 실제 계좌·거래소 자동매매 연결, 수익 보장. (유료로 신호를 계속 보내면 유사투자자문업 문제가 될 수 있어 선을 긋습니다.)
- 의뢰자의 연락처는 공개하지 않습니다. 의뢰 현황에는 동의한 경우 전략 이름과 닉네임만 올립니다.

**지금까지 만든 7개에서 본 것**: 다음 날 방향을 미리 맞히는 규칙은 거의 찾지 못했습니다(4번 효과 미확인, 7번 방향 0~1칸). 대신 언제 크게 움직이는지(7번), 어떻게 하면 덜 잃는지(2번 200일선 필터)는 보였습니다.

## 전략 의뢰 받기 (`requests/`)

1. 메일로 의뢰가 오면 규칙을 되물어 숫자로 정합니다(메일 양식은 첫 화면 “의뢰하기”).
2. `requests/requests.csv`에 한 줄 적습니다: `접수일, 전략, 의뢰자(닉네임만), 상태(접수/진행 중/완료/보류), 결과(machines/이름.html), 공개(Y/N), 메모`. 메모와 공개=N 줄은 사이트에 나가지 않습니다.
3. 구현·백테스트가 끝나면 `machines/이름.html` 결과 페이지를 만들고(아래 “새 결과 페이지 추가하는 법”) 상태를 완료로, 결과 칸에 주소를 적습니다.
4. 이메일·전화번호 같은 연락처가 의뢰자 칸에 들어가면 `requests/build.py`가 멈춥니다(테스트로 검사).

```bash
python3 requests/build.py
python3 -m unittest discover -s requests -p 'test_*.py' -v
```

## 오늘의 한 판 (게임 페이지)

방문자가 들어와서 바로 해 볼 수 있는 판입니다. 매일 한국 시간 오전 9시(바이낸스 일봉 마감)에 회차가 열리고, **내일 오전 9시 비트코인 종가**가 크게 오름 / 횡보 / 크게 내림 중 어디일지 맞힙니다. ‘크게’ = 최근 20일 하루 변동 폭 × 0.5(6번과 같은 방식, 하루 단위). 기준은 `arena/config.json`에 결과를 보기 전에 고정했습니다.

- 선수: 방문자 각자 · 방문자 군중(다수결) · 기계(5번 BREAKOUT·2번 REBOUND 엔진을 그대로, 1번 데모 논조 점수) · 기준선(늘 횡보, 동전 원숭이). 기계의 선택은 방문자가 고른 **뒤에** 보여 줍니다.
- 연습 경기: 기계들이 같은 문제를 2017년부터 매일 풀었다면 — 늘 횡보 49.3%, REBOUND 48.8%, BREAKOUT 47.7%, 1번 데모 규칙 42.2%, 동전 원숭이 34.5%. **늘 횡보가 보스**입니다.
- 투표는 구글 폼 → 시트(5주차 방식) → Actions가 집계합니다. 방문자가 쓴 값이라 믿지 않습니다: 투표 시간 밖·없는 선택지·형식이 틀린 행은 건너뛰고(배포는 멈추지 않음), 한 브라우저당 회차마다 첫 표만 셉니다. 공개 파일에는 방문자 번호를 넣지 않습니다.
- 닉네임 순위: 12자 이내, 한글·영문·숫자·공백·`_.-`만, 링크 불가. 결과가 나온 회차 3번 이상. 시트에 `숨김` 열을 만들고 `Y`를 적으면 그 방문자의 이름을 숨깁니다.
- 폼 연결 전에는 예측이 방문자 브라우저에만 저장됩니다(화면에 그렇게 표시).


## 자동화

`.github/workflows/site.yml` — Pages Source는 **GitHub Actions**입니다.

| 작업 | 하는 일 |
|---|---|
| test | 10개 폴더의 파이썬 테스트(131개), 화면 스크립트 문법 검사. 실패하면 배포하지 않음 |
| build | 플레이 기록(시트 검사), 김프 기록 1건 추가, 오늘의 한 판(투표 집계), 6번 상황 통계, 7번 시간대 지도·2·5번 백테스트(하루 한 번), 공개 파일만 `_site`로 모음 |
| deploy | GitHub Pages에 게시 |

| 실행 조건 | 언제 |
|---|---|
| push | main에 Push할 때 |
| schedule | `cron: "7 * * * *"` — 매시 7분 예약. 실제로는 몇 시간씩 밀리거나 빠짐(첫날 18시간에 3번) |
| workflow_dispatch | Actions 화면의 Run workflow (시트를 고친 뒤) |

- 배포하지 않는 경우: 테스트 실패, 시트 데이터 잘못, 배포된 김프 기록을 읽지 못함 → 이전에 배포한 화면이 그대로 남습니다.
- 계속 배포하는 경우: 시트 접속 실패, 시세 수집 실패 → 이전 결과를 유지하고 경고만 남깁니다.
- 인증키는 쓰지 않습니다. 시트 주소는 공개돼도 되는 값이라 Variables에 둡니다.

## 디자인 원칙

픽셀 오락실 스타일(보라 카펫·픽셀 글꼴 갈무리·오락기 캐비닛·전광판)을 정체성으로 씁니다. 2026-10-01 하루 모던 핀테크로 바꿔 봤다가 “특이성이 없다”는 판단으로 되돌렸고, 그때 얻은 것 중 **차트 가독성**만 남겼습니다.

- 4px 픽셀 단위로 테두리·그림자·간격을 맞춘다. 결과물은 오락기 캐비닛 한 대씩.
- **차트는 픽셀 장식 없이**: 픽셀 화면 안에 흰 차트 판을 끼우고, 일반 글꼴·연회색 눈금·딱 떨어지는 값으로 그린다. 차트마다 위에 “그래서 무슨 뜻인지” 한 줄, 선은 2~3개 이하, 휴대폰에서 짚으면 값.
- 시세 색은 한국 관례: 상승 빨강, 하락 파랑, 항상 ▲▼와 함께. 빨강·파랑은 시세에만 쓰고, 판정·강조는 노랑·민트·분홍.
- 첫 화면 순서: 의뢰소 소개 → “알고리즘 트레이딩, 쉽게 말하면”(5단계·용어 3개) → 진행 방식 4단계 → 결과물 캐비닛 6대 → 의뢰 현황 → 의뢰 양식 → 만든 사람·이용 안내. 게임은 `games.html`.
- 결과 리포트 양식: 머리(종류·이름·질문·핵심 결과·의뢰 버튼·코드 보기) → 쉽게 말하면(비유·단계·규칙 요약표·예시) → 결과(성적, 매매 전략은 “그냥 들고 있었다면” 비교) → 자세히(접힘) → 문의.
- 결과 페이지 머리는 같은 틀: 종류 · 이름 · 질문 · 핵심 결과 · “이런 전략 의뢰하기” 버튼 하나. 바로 아래 “쉽게 말하면”(비유 한 줄 · 단계 흐름 · 숫자 예시). 긴 설명은 “자세히”로 접는다.
- 게임은 가볍게: 고르고, 정답 보고, 끝. 순위·통계 같은 덧붙임은 두지 않는다.
- `prefers-reduced-motion`이면 움직임을 멈춘다. Tab 이동 위치는 어두운 바탕 노랑, 밝은 판넬 진한 테두리.

## 새 결과 페이지 추가하는 법

1. `machines/clock-tower.html`을 복사해 `machines/새이름.html`로 만든다(머리·문의·꼬리 구조 유지).
2. 계산이 있으면 `새이름/config.json`에 기준을 결과 계산 **전에** 고정하고, `build.py`와 `test_build.py`를 만든다.
3. `index.html`의 결과물 카드 목록(`#works .mc-list`)에 카드 한 장(종류·질문·핵심 결과)을 더한다. 결과 페이지 머리(`.mh-*`)에도 같은 내용을 쓰고, 의뢰받은 것이면 `requests/requests.csv` 상태를 완료로.
4. `.github/workflows/site.yml`의 test·build에 새 폴더를 더한다.

- `assets/strategy-lessons.js`, `assets/strategy-lessons.css`: 단계별 차트와 설명, 키보드 조작, 모바일 표시.
- 가격은 임의 단위이며 설명에 쓰는 체결은 수수료·슬리피지·보유 비용을 0으로 두었습니다. 실제 규칙의 신호 시점과 다음 시가 진입, 봉별 손절 적용 순서는 유지합니다.
